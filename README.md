# UIAPduino WebHID Lab

**UIAPduino（HID ProMicro CH32V003）をブラウザから動かすページ集です。**
インストールもアカウントも要りません。Chrome か Edge で開くだけです。

🌐 **サイト URL**: https://tarosay.github.io/uiap-hid-web/

## 何ができるか

- **ブロックでプログラムを作る** — [URB Block Lab](https://tarosay.github.io/uiap-hid-web/uiapruby-block.html)
  はブロックをつなぐと Ruby になって、基板の中で動きます（EEPROM が要ります）
- **Ruby で電子工作をする** — [URB Lab](https://tarosay.github.io/uiap-hid-web/uiapruby.html) /
  [URB EE Lab](https://tarosay.github.io/uiap-hid-web/uiapruby-ee.html) は Ruby の構文で書いて、
  ブラウザでコンパイルして基板へ転送します。数百円から始められます
- **C++ を書いて練習する** — キーボード・マウス・経路探索・迷路・対戦アルゴリズムの練習ページ
- **デバッグする** — HID Console、HID-Serial Bridge、SD カードのファイル操作
- **使い方を調べる** — Arduino IDE のセットアップから書き込みまでの手順

ブロックで動かす方法はもう一つあって、トップページから
[Xcratch + UIAPduino](https://xcratch.github.io/editor/?extension=https://tarosay.github.io/scratch3-uiapduino/uiapduino.mjs)
にも行けます（[リポジトリ](https://github.com/tarosay/scratch3-uiapduino)）。

ブラウザとマイコンは **WebHID API** でドライバなしに直接やり取りします。
GitHub Pages で公開しているので、インストールは要りません。

## URB Lab（UIAPruby）— 数百円から始めるRuby電子工作

| ページ | スケッチ例 | 状態 |
|--------|-----------|------|
| [URB Lab](https://tarosay.github.io/uiap-hid-web/uiapruby.html) | ブラウザ内で生成（コンポーネント選択式） | ✅ 公開中 |
| [URB EE Lab](https://tarosay.github.io/uiap-hid-web/uiapruby-ee.html) | ブラウザ内で生成／**ビルド済みファームを直接書き込み** | ✅ 公開中（24FC256 / CAT24M01WI で実機確認済み） |
| [URB Block Lab](https://tarosay.github.io/uiap-hid-web/uiapruby-block.html) | 同梱ファーム 1 本（`⚙ 準備` から書き込み） | ✅ 公開中（CAT24M01WI の基板で実機確認済み） |

[**Wakayama.rb**](https://wakayamarb.org) コミュニティが開発した、Ruby 構文で UIAPduino を制御できる組み込み Ruby 環境です。
mruby のビルドでは rake が必要な mrbgems の取捨選択と統合を、URB Lab は**すべてブラウザ内**で行います。
PC に Ruby・クロスコンパイラ等のビルド環境を整える必要はありません。

- ブラウザ内の **@ruby/prism WASM** で Ruby コードを AST 解析
- 独自の軽量バイトコード **URB1 形式**（`.urb`）にコンパイル
- **WebHID** で SD カードへ直接転送
- UIAPduino 上の **TinyVM** がバイトコードを逐次実行
- `main.urb` という名前で SD に保存すると、**電源投入時に自動実行**
- 使う機能（コンポーネント ≒ mrbgems）を選ぶと、対応する **TinyVM ファームの .ino をブラウザが生成**。Arduino IDE で書き込むだけ
- **`Tm`（絶対周期）** — `every_ms 100 do … end` は「前回から 100ms」ではなく
  **開始からの絶対時刻**で起こすので、何周回しても周期がずれません。`Timer` で
  区間の実測（ms / µs）もできます。**SD 版・EE 版の両方で使えます**
- インストール不要・クラウド不要

### URB EE Lab — 保存先を I2C EEPROM に替えた版

[URB EE Lab](https://tarosay.github.io/uiap-hid-web/uiapruby-ee.html) は、SD カードの代わりに
**I2C EEPROM**（24FC256 32KB / CAT24M01WI 128KB）にプログラムと `$変数` を保存する版です。
CAT24M01WI は A1 の配線でスレーブアドレスを **0x50/0x51** と **0x52/0x53** のどちらにもできます
（24FC256 と同じバスに載せるときは 0x52 側）。
SD カードを使わないぶん **SPI が丸ごと空き**、その上に載る機能が増えます。

- **BASE が 3,360 B 小さい**（`UIAPrubyVm` 12,504 B → `UIAPrubyEeVm` 9,144 B）。
  コンポーネントに使える余地が約 1.9 倍になり、`Q1` + `Se` + `Np` + `Ec` が同時に載る
- **ビルド不要で始められる** — ビルド済みファームをブラウザから直接書き込めます。
  **Arduino IDE もボードパッケージも要りません**（後述）
- **`Np` / `Nr`（NeoPixel）** — SPI1 が空いたことで初めて可能になった。DIN はピン 8 固定
- **`Se`（UART）** — GPS 受信やマイコン間通信に使える。ピン 15/16
- **`Ev` / `Ec`（EEPROM 変数）** — SD 版の `Ve` / `Sv` に相当。ファイル操作が
  アドレス計算 1 回になり、数値変数は約半分（+1,512 B → +820 B）
- **EEPROM 変数ビューア** — ブラウザから `$変数` の現在値を読み出せる（読み取り専用）。画面に出ている数値配列を **CSV で保存**できる（添字で揃えて縦に並べる）。
  配列の「全部読む」は、途中で読み込みエラーが出ても**読めた要素を残して止まった要素から読み直す**。
  同じ位置で 10 回続けて失敗したら止まり、もう一度押すと続きから読み足す
- ピン 3(SDA) / 4(SCL) は EEPROM が占有。SD 版で塞がっていた 6・7・8・9 は解放
- I2C スレーブは使用不可（自分のプログラムを読めなくなるため）

#### ビルド済みファームを直接書き込む

コンポーネントを選んで `.ino` を生成し Arduino IDE で書き込む道に加えて、
**ビルド済みのファームをブラウザから流し込む**道を用意しました。
`rv003usb` ブートローダ（1209:B803）へ WebHID で書き込みます。

| 選ぶもの | 中身 |
|---|---|
| **サーボ版**（既定） | `Pw` + `Q1` `Ad` `Se` `Np` `Us` `Rn` `Ec` |
| **ブザー版** | `Tn` + `Q1` `Ad` `Se` `Np` `Us` `Rn` `Ec` |
| 自分で選ぶ | 従来どおり。コンポーネントを選んで `.ino` をビルド |

`Tn`（ブザー）と `Pw`（サーボ）は同じタイマーの分周器を共有するため同時に選べません。
**選ぶのは「ブザーか、サーボか」だけ**で、ほかは全部入りです。

ファームはページに base64 で埋め込んであり、焼く前に**生成される `.ino` の SHA-256 を
その場で計算して突き合わせます。**食い違えば書き込まずに止まるので、
「ページだけ新しくてファームが古い」状態で焼くことがありません。

> ✅ **24FC256（32KB）と CAT24M01WI（128KB）の両方で実機確認済み**です
> （プログラム転送・自動実行・`$変数` と配列の読み出し・ブラウザからのファーム書き込み・NeoPixel の動作）。
> CAT24M01WI は **64KB 境界（0x10000）をまたぐ読み書き**も確認しました。
> 電源を切ってからの永続、`Se` のマイコン間通信、ピン 6 の ADC / PWM はこれからです。

### URB Block Lab — ブロックをつないで基板に書き込む

> ✅ **CAT24M01WI（0x50/0x51）を載せた基板で実機確認済み**です。
> 同じロットの 2 枚で、ギャラリーの「LED 点滅」「ボタンで LED ON」を書き込んで動くことを確かめました。

[URB Block Lab](https://tarosay.github.io/uiap-hid-web/uiapruby-block.html) は、
**ブロックを組むと Ruby が出てきて、それが基板の中に入る**ページです。子ども向けの入口として作りました。

Scratch や Smalruby との最大の違いは、**プログラムが PC ではなく基板の中で動く**ことです。
書き込んでしまえば USB を抜いてよく、電源さえあればそのまま動き続けます
（micro:bit の「ダウンロード」・PicoRuby / Arduino の「書き込み」と同じ考え方）。
だからボタンの名前も「動かす」ではなく **「基板に書き込む」** にしてあります。

- **ブロック → Ruby → URB1 → EEPROM。** 後段は URB EE Lab と同じ経路
  （`docs/lib/urb/compiler.js` と `docs/lib/urb/eeprom.js` を両ページで共有）
- **Ruby タブは読み取り専用。** 書き換えたくなったら「UIAPruby で編集する ↗」で URB EE Lab へ渡す
- **サーボの角度は、数を打つほかに変数でも渡せます。**「サーボ ピン ◯ を〈変数〉度にする」に
  `rand` で決めた数を入れれば、動くたびに違う角度へ振れます。
  ただし「サーボの設定」で決めた幅は効きません（`angle` は 50Hz・500〜2400µs 固定）。
  両方を置いたときは、Ruby の先頭に警告コメントが出ます
- **I2C の部品を読み書きできます。**「I2C をはじめる」「アドレス 〈0x48〉 の 〈0x00〉 番地を
  〔変数〕 に 読む」「〜番地に 〔変数〕 を 書く」の 3 つ。アドレスと番地は 16 進（`0x48`）でも
  10 進でも書けます。**値は 0〜255 の普通の数**として扱えるよう、読んだあとに ×256、
  書く前に ÷256 を生成側で入れています（VM では I2C の値だけ Q16.8 ではなく生のバイトで
  出入りするため）。0x50〜0x53 は基板の EEPROM が使っているので、指すと警告コメントが出ます
- **いまできるのは「レジスタから 1 バイト」だけです。** `Wiremin` 自体は n バイトの読み書きも
  レジスタ番号なしの送受信も持っていますが、VM に命令が出ていません。そのため対象になるのは
  LM75 / TMP102 の温度（MSB がそのまま ℃）、MPU-6050 の加速度・角速度（上位バイト）、
  PCA9685 のような書くだけの部品です
- **8×8 の NeoPixel に絵を出せます。**（2 色の「8×8 に表示 ⬛」は 2026-09-19 に引き出しから外しました。
  定義は残してあるので、このブロックで保存した作品はそのまま開けます。いま引き出しにあるのは
  次の項目のパレット版です）「8×8 に表示 ⬛」のマスを押す（押したままなぞる）と、
  micro:bit の「LED 画面に表示」と同じ感覚で絵が描けます。色は 2 つ選べて、
  **えがく色**と**うしろの色**をそれぞれブロックに持たせます（うしろの色は黒＝消灯が既定）。
  テープは **64 個を折り返し（蛇行）でつないである前提**で、**0 番は右上**、上の行は右から左、
  次の行は左から右です
  （画面の `(x, y)` → テープの番号は、`y` が偶数なら `y*8 + (7 - x)`、奇数なら `y*8 + x`）。
  出る Ruby は「うしろの色で `fill` → えがいたマスだけ `set`」なので、
  命令は **6 + 5 × えがいた数** バイトで済みます（全部えがいても 331 B）。
  1 マスごとに `show` が走って絵が描かれていく様子が見えないよう、
  `np.auto = false` で止めてから最後に 1 回だけ送ります。
  **このブロックを置くと LED は 64 個として組み立てます**（「NeoPixel を ◯ 個使う」で
  それより少なく指定していたときは、Ruby の先頭に警告コメントが出ます）
- **色を 8 つ使って絵を描くブロックもあります。**「8×8 に絵を表示」は、マスが**色の番号だけ**を
  覚えます（`0`〜`7` を 64 文字）。色そのものはブロックに並んだ 8 つの色えらび（`いろ`）が持つので、
  **描いたあとに色を変えると絵の色も変わります**。面を開くと、マスの右に大きな色の見本が
  2 列 × 4 段で出るので、えらんでからマスを押します。
  **真っ白から描きはじめます。** 0 番の色（既定は白）が何も描いていないところの色で、LED も白く光ります。
  **「絵を消してはじめから」**（前の「全部消す」）は、絵を消して真っ白にし、ずらしも戻すボタンです。
  色（本体の「いろ」と、えらんでいる色）はそのまま残します（同じ色で描きなおせるように）。
  8 番目の色は **「けす」**（既定は明るさ 0＝光らない）で、
  黒ではなく ✕ の見た目にしてあります（LED では黒は出ないので）。明るさ 0 の色は、どの番号でも
  この見た目になります。面を開いている間は、ブロック本体の「いろ」とボタンは薄くなって押せません。
  **絵を動かせます。** 絵の右の十字で上下左右に 1 マスずつずらせます（8 マスまで）。
  はみ出たところは見えなくなるだけで、反対へずらすと戻ります。ずらして空いたところは斜線になり、
  **描けません**（ずらしても描ける範囲は広がりません）。LED には 0 番の色（白）で送ります。
  `↻` で右に 90 度まわし、`⇋` `⇅` で左右・上下に裏返します（元の絵だけが変わり、ずれはそのまま）。
  **「この絵からはじめる」** は、いま見えている絵を元の絵にした新しいブロックを、
  どこにもはめずにすぐ右下に置きます（斜線だったところも白になり、描けるようになります）。
  ずれていないときは押せません。パラパラ漫画は、ブロックを複製して「待つ」を挟みながら並べ、
  1 コマずつずらして作ります。
  値は元の絵 64 文字のあとに、ずれているときだけ `@dx,dy` を付けます（前の版の 64 文字だけの値も読めます）。
  `np.fill` は「全部塗り」しかできない（Ruby 側は 3 引数のみ）ので、
  **いちばん多く使った色だけをまとめて**、残りを 1 マス 5 バイトで置きます。
  実測で、りんごの絵（3 色）が 175 B、全部同じ色なら 25 B、8 色を総当たりにした最悪で 305 B。
  プログラム領域は 10,240 B なので、**最悪でも 33 枚**ぶん入ります
- **「記録」があります（電源を切っても残る変数）。** Ruby の `$変数` で、URB EE の一番の特徴です。
  「記録 〔スコア〕 を ⟨1⟩ 増やす」「◯ に 書きかえる」「記録 〔スコア〕」の 3 つ。
  **宣言（`$score = $score`）はブロックに出さず、生成側が Ruby の先頭にまとめて出します。**
  読むだけの使い方ができるようにするためと、**宣言の順が変わると EEPROM のスロットがずれて
  記録が消える**ためで、順番は変数を作った順に固定します（あとから増やしても前の記録は動きません）。
  「最初だけ」の中で数に書きかえていると、電源を入れるたびにその値になります。それを警告コメントで
  知らせます（「もし」で囲ってあるときは、そうなるとは限らないので出しません）
- **配列があります。**「変数」の一覧の下に「配列 〔A〕 を 〈4〉 個 つくる」「〔A〕 の 〈0〉 番 を ⟨7⟩ にする」
  「〔A〕 の 〈0〉 番」の 3 つ。**番号は 0 から**で、番号には変数も式（`a[i + 1]`）も使えます。
  中身は全部 0 から始まり、個数はブロックに打った数だけです（変数では決められません）。
  名前は普通の変数と別の型にしてあるので、変数の一覧には出てきません。
  **EEPROM 変数は全部で 6 個まで**で、配列 1 つで 1 個ぶん使います。
  計算のブロックの中に配列の値を入れた形（`b = a[i] + 1`）だけはコンパイラが読めないので、
  Ruby の先頭に警告コメントが出ます
- **繰り返しは 5 つあります。**「◯ 回繰り返す」（`n.times`）のほかに、
  **「⟨条件⟩ の間 / になるまで 繰り返す」**（`while` / `until`）、
  **「繰り返しを抜ける / 次の繰り返しへ」**（`break` / `next`）、
  **「〈1〉 から 〈3〉 まで 〔番号〕 を変えながら 繰り返す」**（`(1..3).each do |i|`）、
  **「つぎの数を 順に 〔数〕 に入れて 繰り返す」**（`[10, 20, 30].each do |ms|`）です
- **while は本物のループで、回数を増やしても命令は増えません**（8 回で 10 命令・50B）。
  「抜ける / 次へ」は繰り返しの外に置くと、ブロックが自分で警告を出して無効になります
- **番号を変えながら回す 2 つは、コンパイル時に回数ぶん本体が複製されます**（TinyVM に
  ループ変数が無いため）。そのぶん命令が増える代わりに、**番号はコンパイル時の定数**になり、
  R0/R1 の枠を使いません。番号は「◯ ミリ秒待つ」「NeoPixel の番号」「配列の番号」に
  そのまま置けますが、**「もし」の条件と「値を表示」には直接置けません**
  （いったん変数に入れます）。展開なので **「抜ける / 次へ」も使えません**
- **「関数」のブロックがあります。**「展開関数を定義」と「展開関数を呼ぶ」で、よく使う手順に
  名前をつけて、置いた場所で呼べます。名前が「展開関数」なのは、この処理系の `def` が
  コンパイルのときに呼び出しの場所へ**丸ごと写される**（インライン展開。TinyVM に呼び出し・
  戻りの仕組みがありません）からです
- **引数は 2 つまで、渡せるのは数だけです。** 引数はコンパイル時に数へ置き換わるので、
  変数は渡せません。**引数の無い関数を呼ぶときは、代わりに ⊕ で「呼ぶ前に」の行を何行でも
  足せます。** 呼ぶ直前にその変数へ値を入れておくと、写された本体がそのまま読みます。数でも変数でも
  式でも置けますが、Ruby の引数ではなく**同じ変数を共有している**だけで、そのぶん変数の枠
  （R0/R1 の 2 つ、3 つ目からは EEPROM 変数）を使います
- **答えを返すのは「判定 ◯ は〈条件〉」と「もし」を組み合わせたときだけです**（`def 名前? … return 条件`）。
  じぶんを呼ぶ形（再帰）は写しが終わらないので、呼び出しの輪を見つけたら Ruby の先頭に
  警告コメントを出して、その呼び出しは出しません
- **比べるブロック・計算のブロックは、丸い差し込み口に数をそのまま打てます。**
  `もし ⟨変数⟩ < ⟨30⟩` のように、「計算」から数のブロックを運ばずに書けます
- **`.rb` で保存 / 開く。** 出てくるのはそのまま動く Ruby で、末尾のコメントにブロックが畳んで入っています。
  読み込むときはそこだけを見るので、**ブロックの位置まで完全に元通り**になります。
  URB Block Lab で保存した `.rb` でなければ、その旨を出して読み込みません
- **タブをまたいでブロックをコピー / 貼り付け。** Ctrl+C / Ctrl+X / Ctrl+V と、右クリックの
  「コピー」（ブロック）・「貼り付け」（机）で、別のタブの作品にブロックを持っていけます。
  コピーした中身はこのブラウザの localStorage に置きます。変数は**名前と種類で**貼り付け先の変数に付き、
  無ければ作ります。同じ名前で種類（ふつう / 記録 / 配列）が違う変数があるときは、
  貼る側を `かず2` のように名前をずらします
- **ギャラリーへの入口。** ブロックの一覧（「変数」）の下に **URB ギャラリー ↗** を置いてあります。
  押すと別のタブで [URB ギャラリー](https://tarosay.github.io/urb-gallery/)が開きます
  （いま組んでいる作品からは離れません）
- **ギャラリーから開ける。** `?rb=<作品の id>` を付けて開くと、
  [URB ギャラリー](https://tarosay.github.io/urb-gallery/)の作品を**新しい作品として**読み込みます。
  受け取るのは id だけで、取りに行く先（`/urb-gallery/works/`）はページ側が持っているので、
  リンクで知らない場所を読ませることはできません
- **作品はいくつも持てる。**「新しく作る」は別のタブに白紙の作品を開きます。
  作品名はヘッダで変えられて、**ブラウザのタブの見出しにもなる**ので、並べたタブを見分けられます
- **`⚙ 準備`（大人の方へ）** — ファームウェアの書き込みはここに入れてあります。基板 1 台につき一度だけ
- **基板のファームウェアを調べる（`⚙ 準備` の中）** — 書き込みモード（ボタンを押しながら USB）の基板から
  Flash を読み出し、これまでに配ったファームと SHA-256 で照合して、どの版が入っているかを出します。
  読むだけで書き換えません。ファームに版番号を持たせていないので、**すでに配った基板も見分けられます**。
  古い版や URB EE Lab のファームウェアだったときは、**書き込みモードのまま**「ファームウェアを書き込む」へ案内します
  （USB を挿し直さずに、そのまま書き換えられます）
- **`■ 緊急停止` / `▶ 再開`** — 引き出しのバーから、基板で動いているプログラムを止めたり動かし直したり
  できます。`wait` の無いループを走らせていると書き込みが通らないことがあるので、その復帰用です。
  **基板につながっていなくても押せます。**押すと基板を選ぶ画面が出て、選んだら STOP / RUN だけを送ります（書き込みはしません）
- **基板へのつながり方** — 一度選んだことのある基板は、ページを開いたときと **USB を挿したとき**に自動でつながります。
  初めての基板は「■ 緊急停止」「▶ 再開」「基板に書き込む」のどれかで選びます
- **下の引き出し（ログ / コンソール）** — 自動で開くのは、**エラーのとき**と、
  **「基板に書き込む」「▶ 再開」のあと「と表示する」（`puts`）の出力が最初に届いたとき**です。
  出力が続いても開くのはその 1 回だけなので、閉じれば次に書き込むか再開するまで開きません（ブロックを隠さないため）。
  書き込みの経過を見たいときは「▲ ログ / コンソール」で開きます
- **必要な EEPROM は CAT24M01WI（0x50/0x51、A1 = L）。** URB EE Lab で CAT24M01WI を
  選ぶときと**同じ石・同じ配線**で、基板はそのまま使えます。**24FC256 の基板では動きません。**
  ブロックが吐く Ruby は手書きより冗長になりやすいので、プログラム領域を 2,560 B → 10,240 B に
  広げてあり、その広さは 128 KB の CAT24M01WI でないと取れないためです
- 構成は 1 つに固定（`Q1` `Pw` `Ad` `Se` `Nr` `Us` `Rn` `Ev`）で、**プログラム領域を広げた
  専用ファーム**を同梱しています（`tools/build-block-bin.mjs` が生成）

> 複数のタブ・URB EE Lab からも同じ基板に同時につながり、どこからでも停止 / 再開できます。
> ただし基板とのやり取りは 1 つずつで、**ほかのタブが書き込んでいる間は、書き込み・停止・再開を断ります**
> （「ほかのタブが基板に書き込んでいます」と出ます。終わってから押し直してください）。

### コンポーネント一覧

BASE（GPIO / wait_ms / if / unless / until / case-when / loop / for / while / && / || / puts "文字列" / `warn` デバッグ出力 / def（引数付き最大2個） / require）= **12,964 B**。
そこに必要な機能だけを足して、16 KB の Flash に収めます。

| ID | 内容 | Flash 増分 |
|----|------|-----------|
| Q1 | Q16.8 固定小数点演算（四則演算・比較・case/when・ラムダ式） | +592 B |
| Tn | Tone — 周波数制御（ブザー・メロディ） | +1,008 B |
| Pw | PWM デューティ比（モータ・サーボ・LED調光） | +548 B |
| Ad | ADC アナログ入力（整数 0〜255） | +328 B |
| Us | 超音波センサ HC-SR04（距離 cm） | +156 B |
| I2 | I2C / Wire（SDA=pin3 / SCL=pin4・100kHz） | +1,448 B |
| Rn | 乱数 rand / srand | +196 B |
| Tm | 絶対周期 — ずれない周期（`every_ms`）と時間計測（`Timer`） | +384 B |
| Ve | 変数の拡張 — 数値SD変数（`$`永続変数・3つ目以降の数値変数・数値配列。確認は `warn`） | +1,516 B |
| Sv | SD変数・数値出力（PRINT_REG・文字変数・to_s。**Ve の機能を含む**） | +2,832 B |

> `warn 変数` は数値を **DEVICE LOG** へ送るデバッグ出力（Ruby の `Kernel#warn` = stderr に相当）。
> 数値の文字列化をブラウザ側で行うため **Sv 不要**で使えます（Q1+Sv 構成のみ Flash 16KB 超過のため非搭載 — `puts`/`p` で代替）。

## 各ページの機能

### HID-Serial Bridge（デバッグ / ユーティリティ）
- UIAPduino の **HID通信**を **WebCom通信**（Web Serial API）経由で仮想 COM ポートへ中継するブリッジ
- **com0com**（仮想 COM ペアドライバ）で作った VirtualCOM 通信ペアを使い、Arduino IDE シリアルモニタ／TeraTerm・Python・C# などと UIAPduino をシリアル通信感覚でつなげる
- HID と WebCom 両方の接続が完了すると**ブリッジを自動開始**
- **HID受信モード**: Protocol モード（デフォルト）と Raw Binary モードを切替可能
  - **Protocol モード**: `0x50`/`0x52` パケットをデコードしてテキスト・バイナリを WebCom 通信へ転送（`HidMonitorTest` スケッチ向け）
  - **Raw Binary モード**: 全バイトをそのまま WebCom 通信へ転送（`HidBridgeTest` スケッチ向け）
- モード切替でスケッチビューアが対応スケッチに自動切り替わる
- WebCom 通信 → HID通信：常に Raw。Feature Report サイズ単位でバッファリング + 30 ms タイムアウトフラッシュ
- HID 接続時に接続通知（`0x01` Feature Report）を送信し UIAPduino の `WaitAvailable()` を解除
- Feature Report サイズをデバイスの HID ディスクリプタから**自動検出**
- ページ内にセットアップガイド（com0com インストール・設定・使い方）とプロトコル仕様を掲載

### HID Console（デバッグ / ユーティリティ）
- Arduino の `hid.Print()` / `hid.Println()` / `hid.Clear()` 出力をブラウザでリアルタイム表示（緑端末 UI）
- HID 接続時に接続通知（`0x01` Feature Report）を送信し UIAPduino の `WaitAvailable()` を解除
- `0x53` Ready 通知を受信してログ表示
- DEC / HEX / ASCII モードで任意データを送信 → Arduino 側 `hid.Recv()` で受け取り
- Feature Report サイズをデバイスの HID ディスクリプタから**自動検出**
- バイトプレビューグリッドで送信内容を確認しながら入力
- 送受信ログ（タイムスタンプ付き TX / RX）
- ページ内にプロトコル仕様を掲載

### HID 接続チェック（デバッグ / ユーティリティ）
- **基板がつながらないときに、どこで止まっているかを切り分ける**ための診断ページ。スケッチ不要・1 ファイル完結・外部ライブラリなし
- ① この環境: `navigator.hid` の有無 / `window.isSecureContext` / `location.protocol` / `userAgent`
- ② 許可済みの機器: **ページを開いた時点で `getDevices()` を自動実行**。0 件なら「まだどの HID 機器にも許可を与えていません」と表示。「もう一度調べる」ボタンあり
- ③ デバイス選択: ボタンを押したときだけ `requestDevice({ filters: [] })` を実行（**1 クリックにつき 1 回**）。フィルタを掛けないので、ダイアログがそもそも出るかどうかが分かる
- 機器ごとに `productName`（空文字なら「(空文字)」）/ `vendorId` / `productId` を 10 進と 16 進で表示
- **`usagePage`/`usage` を collections の全数ぶん表示**（正常な UIAPduino は `0xFF00/0x0001`）
- 失敗時は `error.name` と `error.message` の**両方**を画面に出す
- ③ の実行後は ② を取り直すので、許可が増えたかどうかも分かる

- 変換後の `.midb` を SD カードに入れ、`MidbPlayer.ino` を書き込んだ UIAPduino SD に接続した SAM2695 で再生

### Snake Solver（経路探索アルゴリズムの練習）
- UIAPduino が 16×16 の盤面で岩を避けながら指定ステップ数伸び続けるレベル制ゲーム
- Web ページがゲームを進行し、UIAPduino は `snake.sendDir(dx, dy)` で次の方向を返すだけ
- 実装済みアルゴリズム: BFS 最大空間優先（岩があっても最も広い空間へ進む）
- レベルクリアごとに岩が 3 個増加、失敗しても同レベルで岩・スタート位置を変えてリトライ
- `SnakeHID` クラス（`SnakeHID.h`）に通信をカプセル化、C++ クラス設計の練習も兼ねる

### Rock Dodge（リスクとリターンの判断を学ぶ）
- 落ちてくる岩をよけながら**得点アイテム**を拾うレベル制ゲーム（全レベル 120 ステップ固定）
- **セーフティライン**（画面の水色）に乗っている限り岩には絶対に当たらない。岩の湧きは毎回
  「ライン上の仮想プレイヤーが生き残れること」を検証してから配置される
- ただし乗っているだけでは**アイテムノルマ**（Lv1 で 6 個 → Lv5 で 10 個）に届かずゲームオーバー。
  安全運転で取れるのは 1 面 7〜9 個なので、**得点はラインを外れた先にしかない**
- アイテムの得点は「ラインを何ティック外れる必要があるか（リスク d）」に連動。
  得点の帯は互いに重なっているので「浅いのに高いアタリ」「深いのに安いハズレ」がある
- **壁の岩の一部が 2〜4 列つながってアイテムに変わる**（隙間とは別の開口部）。奥へ入るほど高得点
- ラインから 2 列以上離れると湧きが敵対化 — 壁の隙間がラインの位置に寄り、
  **盤面の途中（12 行目・猶予 3 ティック）から狙い岩**が降ってくる
- ★（面クリアアイテム）は得点 0 で即クリア＋ノルマ免除。深い位置に湧くので、
  順調なときは踏まないように**避けるのが正解**
- **脱出路の仕掛け**: 壁の奥のお宝には、数ティック後の壁に「そこから届く★」が
  仕込まれることがある（深いお宝の約 4 割）。詰み確定に見えて狙える状況を意図的に作っている
- 配布スケッチは時空間先読みで生存＋±1 列のタダ取りまで（岩には当たらないがノルマ壁で止まる）
- ランキングは localStorage に名前つきで保存（名前は `#define PLAYER_NAME`）

### Snake VS（対戦アルゴリズムの練習）
- 16×16 の盤面で 2 匹が**毎ティック 1 マス成長**し、壁・岩・どちらかの体に触れたら死亡。
  生き残ったほうがラウンド勝ち。頭が同じマスに入る／頭を入れ替える動きは両者死亡＝引き分け
- **vs CPU（1台）**: CPU 5 段ラダー（ランダム → 貪欲 → BFS 最大空間 → **ボロノイ** →
  ボロノイ＋先読み）を 3 本勝負（2 本先取）で勝ち上がる。ランキングは撃破した最高レベル
- **2P 対戦（2台）**: UIAPduino 2 台で直接対戦。**5 本勝負**で引き分けも 1 本として数え、
  勝ち数が多いほうが勝ち（同数なら試合も引き分け）。ランキングは**連勝記録**
  （負けても引き分けても 0 に戻るので、自然に勝ち抜き戦になる）
- **相手の体は「相手の頭の軌跡」**。縮まないので、頭の座標 2 バイトを送るだけで
  デバイス側が相手の体を完全に復元できる（盤面全体を送る必要がない）
- スタート位置は **180° 回転対称の 6 パターン**からラウンドごとにランダム。
  どのパターンでも位置の有利不利が生じない（開始時の陣地が 115 対 115 で一致することを実測）
- **ロックステップ進行** — 相手の `CMD_DIR` を待ってから次のティックへ進むので、
  USB の遅延や計算時間では勝敗が決まらない（2 秒タイムアウト・3 回連続で反則負け）
- 開始時に「**3・2・1・スタート**」のカウントダウン。この時間で準備通信（RESET → 岩 → START）を
  済ませるので、待ち時間がそのまま演出になる。2P では 2 台ぶんの準備をこの窓が吸収する
- **陣地（ボロノイ図）の可視化トグル** — どちらが先に到達できるかを色分け表示。
  観客に優勢が一目で伝わり、挑戦者には CPU Lv4 が何を最大化しているかが見える
- 効果音（WebAudio で合成・音源ファイル不要）とミュートトグル
- `SnakeVSHID` クラス（`SnakeVSHID.h`）に通信をカプセル化

### Maze Solver（迷路探索アルゴリズムの練習）
- Web ページが生成した迷路を UIAPduino が **WebHID 経由**でリアルタイムに探索するゲーム
- `maze.sense(x, y)` / `maze.moveTo(x, y)` の 2 関数だけでアルゴリズムを実装できる
- スケッチに実装済みのアルゴリズム:
  - **右手法**（Wall Follower）
  - **DFS**（深さ優先探索）
  - **Greedy DFS**（マンハッタン距離でゴール方向を優先する DFS）
  - **BFS**（幅優先探索・最短経路保証）
- WebHID 通信の詳細を `MazeHID` クラス（`MazeHID.h`）に分離し、C++ クラス設計の練習も兼ねる
- Web 側でも BFS による **回答表示**（ゴールまでの最短経路をキャンバス上に緑表示）が可能

## WebHID 通信の概要

```
[Web ブラウザ]                              [UIAPduino]
 sendFeatureReport()  ─── EP0 ──────────►  usb_handle_user_data()
                         Control Transfer        ↓
                         32 バイト（v1.1.5 以降）  WebHID.recv()  /  hid.Recv()

 inputreport イベント  ◄─── EP3 ──────────  WebHID.send()  /  hid.Print()
                         Interrupt IN           ↑
                         8 バイト / 10ms   usb_handle_user_in_request()
```

| 方向 | エンドポイント | プロトコル | サイズ |
|------|--------------|-----------|--------|
| Web → デバイス | EP0 | Control Transfer (Feature Report) | スケッチの `recv` バッファサイズに依存 |
| デバイス → Web | EP3 | Interrupt IN | 8 バイト / パケット |

> **Feature Report サイズについて**  
> arduino_core_ch32 **v1.1.5** で Feature Report サイズが **16 → 32 バイト** に変更されました。  
> スケッチ内の `WebHID.recv(buf, sizeof(buf))` に渡すバッファサイズが、  
> USB ディスクリプタに登録される Feature Report サイズになります。  
> ブラウザは接続時にディスクリプタを読み取り、そのサイズに合わせた `sendFeatureReport()` のみ受け付けます。  
> 各ページはデバイス接続時にサイズを自動検出し、UI に反映します。
>
> | ボードパッケージ | Feature Report サイズ |
> |-----------------|----------------------|
> | arduino_core_ch32 v1.1.3 以前 | 16 バイト |
> | arduino_core_ch32 v1.1.5 以降 | 32 バイト |

> **USB Low Speed の制約**  
> Interrupt エンドポイントの最大パケットサイズは **8 バイト**固定。  
> 16 バイト以上を返す場合は 8 バイトずつ複数回 `WebHID.send()` を呼ぶ。

### 通信インターフェイス定義

| 用語 | 区間 | 技術 |
|------|------|------|
| **HID通信** | UIAPduino ↔ ブラウザ | USB HID（WebHID API）|
| **WebCom通信** | ブラウザ ↔ 仮想COMポート | Web Serial API |
| **VirtualCOM通信** | 仮想COMペア内部（COM8 ↔ COM9）| com0com |
| **COMモニタ通信** | 仮想COMポート ↔ モニタアプリ | シリアル通信 |

### マーカーバイト一覧

| マーカー | 名称 | 方向 |
|---------|------|------|
| `0x50` | Print | UIAPduino → ブラウザ |
| `0x51` | GetPos | 双方向 |
| `0x52` | Write | UIAPduino → ブラウザ |
| `0x53` | Ready | UIAPduino → ブラウザ |
| `0x01` | 接続通知 | ブラウザ → UIAPduino |

### プロトコル仕様

**Print（`0x50`）** — `hid.Print()` / `hid.Println()` / `hid.Clear()`

| byte | 内容 |
|------|------|
| 0 | `0x50`（マーカー） |
| 1 | flags: `0x80`=続きあり / `0x04`=クリア |
| 2〜7 | テキスト本体（最大 6 文字、`0x00` 埋め） |

※ 改行は `0x0A` をテキストに含めて送信（NL フラグは廃止）

**Write（`0x52`）** — `hid.Write()`

| byte | 内容 |
|------|------|
| 0 | `0x52`（マーカー） |
| 1 | flags: `0x80`=続きあり |
| 2 | ペイロード長（0〜5） |
| 3〜7 | バイナリペイロード |

**Ready（`0x53`）** — `hid.Ready()`（任意使用）

| byte | 内容 |
|------|------|
| 0 | `0x53`（マーカー） |
| 1〜7 | `0x00`（予約） |

**接続通知（`0x01`）** — HID接続時にブラウザが送信

| byte | 内容 |
|------|------|
| 0 | `0x01`（接続通知マーカー） |
| 1〜 | `0x00`（未使用） |

UIAPduino 側の `hid.WaitAvailable()` がこれを検出して処理を開始する。

## Hid クラス API

`HidBridgeTest` / `HidMonitorTest` / `HidPrint` スケッチで共通して使用する `Hid` クラスのメソッド一覧。

| メソッド | プロトコル | 説明 |
|---------|-----------|------|
| `Print(const char* s)` | `0x50` | テキスト送信（改行なし）|
| `Print(int v)` | `0x50` | 整数送信（改行なし）|
| `Println(const char* s = "")` | `0x50` | テキスト送信 + 改行（`0x0A`）|
| `Println(int v)` | `0x50` | 整数送信 + 改行（`0x0A`）|
| `Clear()` | `0x50` CLEAR | 画面クリア |
| `Write(const uint8_t* buf, uint8_t len)` | `0x52` | バイナリ送信（`0x00` 含むデータも正確に転送）|
| `Send(const uint8_t* buf, uint8_t len)` | Raw | マーカーなし Raw 送信 |
| `Ready()` | `0x53` | 準備完了通知（任意）|
| `Recv(uint8_t* buf, uint8_t maxLen)` | — | Feature Report 受信。戻り値: 受信バイト数 |
| `WaitAvailable(uint32_t timeoutMs = 0)` | — | Feature Report 到着まで待つ。**データを消費しない**。`0` = 無限待ち |
| `GetPos(int16_t& x, int16_t& y)` | `0x51` | カーソル座標取得。500 ms タイムアウト |

> **LTO（Link Time Optimization）について**  
> CH32V003 は Flash 16 KB。LTO が有効なため、スケッチで使用しないメソッドはビルド時に自動削除されます。

### 2026-09-04

**「記録」（電源を切っても残る変数）のブロックを足した**

- 「変数」の一覧の下に **「記録 ◯ を ◯ 増やす」「記録 ◯ を ◯ に 書きかえる」「記録 ◯」** の
  3 つを足しました
- **宣言は生成側が先頭に出します。** 記録は宣言しないと読めず（`warn $count` だけではエラー）、
  さらに**宣言の順が変わると EEPROM のスロットがずれて記録が消えます**。
  ブロックを並べ替えても順が動かないよう、変数を作った順で先頭に固定しています
- **「最初だけ」で書きかえているときは、事実だけを知らせます。** 記録は電源を入れるたびに
  その値になります。そうしたいのか記録を残したいのかは書く人が決めることなので、
  警告コメントに「こうしなさい」は書きません。「もし」で囲ってあるときは、
  電源のたびにその値になるとは限らないので出しません
- 記録に 0 以外の始まりの値を持たせたいときは、
  「もし ⟨記録 ◯ = 0⟩ → 記録 ◯ を ◯ に 書きかえる」で書けます
- **名前は ASCII に落とします。** URB1 は変数名を 1 文字 1 バイト（`charCodeAt(0) & 0xFF`）で
  書くため、日本語のままだと EEPROM の中で化けて、基板の変数一覧でも読めません。
  英数字だけの名前はそのまま、日本語の名前は画面の名前から作った `rec****` にします
  （同じ名前なら いつでも同じ記録になります）
- **記録と配列は合わせて 6 個まで**（EEPROM 変数の枠）。超えたら警告コメントを出します

**I2C マスターのブロックを足した**

- **「I2C」のカテゴリ**を新しく作り、**「I2C をはじめる」「アドレス ◯ の ◯ 番地を 〔変数〕 に 読む」
  「アドレス ◯ の ◯ 番地に 〔変数〕 を 書く」** の 3 つを置きました。
  通信（シリアル）とは分けています。今後、部品ごとのブロックが増える場所になるためです
- **値の換算を生成側で入れています。** VM の I2C は値だけ Q16.8 ではなく生のバイトなので
  （`regs[dst] = (int32_t)val;` / `regs[src] & 0xFF`）、読んだら ×256、書く前に ÷256 して、
  アナログ入力や NeoPixel の色と同じ 0〜255 にそろえました。書くほうは元の変数を割ってから
  掛けて戻します（一時変数を作ると R0/R1 を食うため）
- **アドレスと番地は 16 進でも 10 進でも書けます**（`0x48` / `72`）。範囲外や数でない入力は
  ブロックが受け付けません。0x50〜0x53 は基板の EEPROM が使っているので警告コメントを出します
- できるのは「レジスタから 1 バイト」だけです。`Wiremin` は n バイトもレジスタ番号なしの
  送受信も持っていますが、VM に命令が出ていないためです

**番号を変えながら回す繰り返しを 2 つ足した**

- 「繰り返し」に **「〈1〉 から 〈3〉 まで 〔番号〕 を変えながら 繰り返す」**（`(1..3).each do |i|`）と
  **「つぎの数を 順に 〔数〕 に入れて 繰り返す」**（`[10, 20, 30].each do |ms|`。⊕ で個数を増やす）を
  足しました
- **`for` ではなく `each` を出します。** Ruby では `for` は勧められない書き方で、
  `for i in 1..3` と `(1..3).each do |i|` は同じ 21B です。Ruby タブは読み物でもあるので
  `each` にしました
- **番号の使えるところ／使えないところを確かめました。** `wait_ms i` / `np.set(i, …)` /
  `a[i] = i` / `i * 100` は通り、`if i > 1` と `warn i` は通りません
  （どちらも「Q16.8: 左辺は数値変数である必要があります」等。いったん変数に入れれば通ります）
- **`break` / `next` はこの 2 つの中では使えません**（展開されるため `break outside of loop`）。
  `loopTypes` に登録していないので、置いてもブロック側が無効にします
- なお `3.times do |i|` と `1.upto(3)` はコンパイラが読めないので、番号が要るときはこの 2 つを使います

**配列のブロックを足した**

- 「変数」の一覧の下に **「配列 ◯ を ◯ 個 つくる」「◯ の ◯ 番 を ◯ にする」「◯ の ◯ 番」** の
  3 つを足しました
- **番号は 0 から。** Ruby も C も 0 始まりなので、ブロックに打った数字と出る Ruby の数字が一致します
- **名前は専用の型（Array）**にして、普通の変数の一覧に混ざらないようにしました
- **計算のブロックの中では使えません。** `b = a[i] + 1` はコンパイラが読めません
  （`a[i] = a[i] + 1` と `if a[i] > 5` は読めます）。この形を見つけたら、
  Ruby の先頭に警告コメントを出します
- 個数はブロックに打った数だけ（`Array.new(n)` は不可）、EEPROM 変数は全部で 6 個まで
  （配列 1 つで 1 個ぶん）です

**繰り返しに while と break / next を足した**

- **「⟨条件⟩ の間 繰り返す」**（`while`。ドロップダウンで `until`）と
  **「繰り返しを抜ける / 次の繰り返しへ」**（`break` / `next`）を「繰り返し」に足しました。
  それまで「◯ 回繰り返す」しかなく、回数の決まらない繰り返しが書けませんでした
- **「抜ける / 次へ」は Blockly 標準のブロックです。** ただし標準の言い回し
  （「ループから抜け出す」「ループの次の反復処理を続行します」）は硬いので `Blockly.Msg` で差し替え、
  「ずっと」と「〜の間 繰り返す」を `loopTypes` に登録しました。登録しないと、正しく置いても
  標準ブロックが自分を無効にしてしまいます
- **「〜の間 繰り返す」は独自ブロックです。** 標準の `controls_whileUntil` は
  「繰り返す：続ける条件 ⟨…⟩」と、条件より先に言葉が来て日本語の順になりません

**「関数」のブロックを追加した**

- **`def` を出すブロックが 1 つも無かった**ので、「関数」のカテゴリを足しました。
  「展開関数を定義」（引数 0 / 1 / 2 個）・「展開関数を呼ぶ」・「判定を定義 ◯ は〈条件〉」
  （`def 名前? … return 条件`）・「判定 ◯」の 6 個です
- **名前を「展開関数」にしたのは、この処理系の `def` がぜんぶインライン展開だからです。**
  TinyVM に呼び出し・戻りの仕組みが無く、本体は呼び出しの場所へ丸ごと写されます
- **コンパイラの決まりは、ブロックの形のほうで守らせています。** 引数は 2 つまで・
  渡せるのは数だけ（丸い差し込み口ではなく入力欄にしてあります）・
  値を返せるのは「もし」の条件だけ（`return` 1 行）です
- **引数の無い関数には ⊕ で「呼ぶ前に」の行を何行でも足せます。** 呼ぶ前にその変数へ値を入れておくと、
  写された本体がそのまま読みます。Ruby の引数ではなく同じ変数を共有しているだけなので、
  いくつでも渡せる代わりに変数の枠を使います。「呼ぶ」ブロックは 1 つで、選んだ関数が
  引数付きなら数の欄に、引数なしなら変数の行に変わります
- **じぶんを呼ぶ形（再帰）は出しません。** 写しが終わらずコンパイラが止まらなくなるので、
  呼び出しの輪を先に見つけて、Ruby の先頭に警告コメントを出します。
  名前が無い呼び出しも同じ扱いです
- **名前は 1 つずつ。** 同じ名前を付けると後ろに数が付きます。名前を変えると、
  それを指している「呼ぶ」も一緒に付け替えます

**URB Lab / URB EE Lab — 新コンポーネント `Tm`（絶対周期）を両方に追加**

- `sleep` を並べて周期を作ると、本体にかかった時間のぶん毎周ずれていく。
  **`every_ms` は起点を持ち、「前回起点 + 周期」で進める**ので誤差が累積しない。
  1000 周まわしても `n × 周期` がそのまま経過時刻になる
- 書き方は 2 通り。**ブロックの形 `every_ms 100 do … end` と、
  `loop do` の中に置く文の形 `every_ms 100`。**バイトコードは同じ 1 命令
- **`Timer` で区間の時間を測れる** — `t.ms`（上限 89.4 秒 / 1ms）と
  `t.us`（上限 8.38 秒 / 1µs）。**読んでも起点は動かない**ので同じ区間を両方読める。
  区間を区切るのは `t.reset`
- **起点は「書いた場所ごと」**に持つ（共有プール 8 個）。1 つで共有すると、
  入れ子にしたときに外側の周期が黙って倍になる。`every_ms` と `Timer` の起点は
  **完全に独立**で、周期の境目で `Timer` が区切られることはない
- 本体が周期を超えた周は待たずに進み、起点を現在時刻にして遅れを捨てる
- 命令は `EVERY_MS` 0x47 / `TIMER_RESET` 0x48 / `TIMER_MS` 0x49 / `TIMER_US` 0x4A。
  番号は決定 27（新規の未使用領域に連続確保・既存番号は使い回さない）に従う
- **Flash 実測は EE 版 +580 B**（BASE 9,304 → 9,884 B）、**SD 版 +384 B**（12,664 → 13,048 B）。
  SD 版が安いのは BASE が除算ヘルパを既にリンクしているため。RAM はどちらも起点 8 個で 32 B
- **EE 版の配布 bin 6 種には入っていない**（ブザー版が残り 52 B しかなく、実測で溢れた）。
  「自分で選ぶ」で `Tm` にチェックを入れて `.ino` をビルドする。
  **6 種の `.bin` と `inoSha256` は 1 バイトも変わっていない**
- サンプル 3 つを追加 — `tm-blink` / `tm-jitter` / `tm-react`。3 つとも **`Tm` 単独で動く**
- **2 ページで命令番号・動作・Ruby 記法は完全に同一。**どちらも実機で動作確認済み

**URB Lab — サーボ angle() を 50Hz 標準タイミング化 + ファーム MUL_Q16 の乗算バグ修正**

- **MUL_Q16 を int32 乗算に修正**（積 ±32768 未満まで正確）。Q1 系 4 スケッチ
  （UIAPrubyVmQ1 / Q1Pw / Q1Sv / Q1Tn）を再生成 — **書き込み済みボードは再書き込みが必要**

**通信インターフェイスの用語定義**  
「Serial」という言葉の混同を避けるため、通信区間ごとに用語を定義した。  
HID通信 / WebCom通信 / VirtualCOM通信 / COMモニタ通信

**Hid クラスの大幅拡充（HidBridgeTest / HidMonitorTest / HidPrint 共通）**
- `WaitConnect()` を廃止し `WaitAvailable(uint32_t timeoutMs = 0)` に改名

**HidMonitorTest スケッチ新規追加**

## 新しいデモページを追加するには

1. `docs/` に新しい HTML ファイルを作成（例: `docs/newdemo.html`）
2. ページ上部に戻るリンクを追加
   ```html
   <a href="index.html">← UIAPduino WebHID Lab</a>
   ```
3. スケッチを `docs/sketches/スケッチ名/スケッチ名.ino`（以降は同フォルダに `.h` / `.cpp` も追加可）として配置
4. `docs/index.html` にリンク付きカードを追加（Coming Soon カードがあればそれを置き換える）
5. `README.md` を更新 — **忘れやすいので 4 箇所すべて**:
   - 「デモページ一覧」テーブルに行を追加
   - 「各ページの機能」に説明を追加
   - 「ファイル構成」に HTML とスケッチフォルダを追加
   - 「変更履歴」に日付つきで追記
6. コミット＆プッシュ → GitHub Pages に自動反映
